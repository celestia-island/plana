# refactoring_guide

## Description

Generates refactoring guidance by identifying code smells, proposing mechanical transformations with safety validation, and producing a ranked refactoring plan. Each suggestion includes before/after code, affected scope, risk assessment, and verification steps.

## Preconditions

- Target scope is defined (file, function, or module)
- LSP server for the target language is available
- Container is available in Read mode (analysis only, no modifications)

## SOP

### Step 1: Smell Detection

```bash
$ code_review(file_path=<path>, content=<content>)
$ static_analyze(file_path=<path>, content=<content>, checks=["dead_code", "structural_patterns"])
```

- Identify code smells with specific locations and categories
- Classify severity:
  - **Structural**: god objects, feature envy, inappropriate intimacy
  - **Complexity**: long methods, deep nesting, callback hell
  - **Duplication**: copy-paste code, parallel inheritance hierarchies
  - **Naming**: unclear names, inconsistent terminology
- **Gate**: If no smells detected → return `"Code is clean. No refactoring needed."`

### Step 2: Impact Analysis

For each detected smell:

```bash
$ lsp_symbols(file_path=<affected_file>, depth="references")
```

- Map all symbols affected by the potential refactoring
- Count downstream consumers (callers, importers, dependents)
- Compute blast radius: `affected_files × affected_symbols × external_consumers`
- **Gate**: If blast radius > threshold (configurable, default: 10 files) → mark as "requires team coordination"

### Step 3: Transformation Proposals

```bash
$ refactor_suggest(
  smells=<detected_smells>,
  prioritize="safety_impact_ratio",
  constraints=["preserve_public_api", "no_behavior_change"]
)
```

- Generate specific transformation proposals:
  - **Extract method**: `long_function() → helper_a() + helper_b() + orchestrator()`
  - **Extract class**: `GodObject → DataService + BusinessLogic + IOAdapter`
  - **Replace conditional with polymorphism**: `match/if-else chain → trait/strategy`
  - **Introduce parameter object**: `(a, b, c, d) → ConfigParams { a, b, c, d }`
- Each proposal includes:
  - Before/after code sketch
  - Affected files and symbols
  - Estimated effort (lines changed, files touched)
  - Risk level (mechanical / needs-review / needs-design)

### Step 4: LSP Validation

For each transformation proposal:

```bash
$ lsp_refactor(file_path=<path>, refactor_type=<type>, range=<range>)
```

- Validate the refactoring is supported by the language server
- Check: will the refactoring compile? Are there type errors?
- **Gate**: If LSP reports errors for the proposed change → mark as "needs manual adjustment"

### Step 5: Ranked Refactoring Plan

- Sort proposals by: `(impact_score × safety_score) / effort`
- Group into waves:
  - **Wave 1**: Mechanical transforms (safe, no behavior change, high confidence)
  - **Wave 2**: Localized restructuring (limited scope, may need review)
  - **Wave 3**: Cross-cutting redesign (team coordination required)
- Each wave should be independently completable

### Step 6: Report

```bash
$ report(
  summary="Refactoring guide: <N> proposals in <W> waves, <M> mechanical, <K> needs-review",
  body=<refactoring_plan_json>,
  severity="low",
  waves=<wave_details>,
  total_effort_estimate="<lines_changed> lines across <files> files"
)
```

## Postconditions

- Ranked refactoring plan with before/after code sketches
- LSP-validated safe transformations marked
- Waves independently executable
- No changes applied (read-only; use `refactoring_workflow` to execute)

## Decision Philosophy

@system/decision-philosophy

**Skill-specific principles:**

- **Mechanical first**: Prefer automated, safe transforms over manual restructuring
- **Preserve public API**: Refactoring should not break downstream consumers
- **Validate before proposing**: Use LSP to confirm feasibility before recommending
