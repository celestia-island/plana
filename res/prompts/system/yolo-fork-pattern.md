# YOLO Fork Pattern

This document defines the shared heuristic for when a YOLO-invoked skill should fork a new `#demiurge.xxx` task instead of attempting work inline. YOLO skills reference this with `@system/yolo-fork-pattern`.

## Core Principle

YOLO tasks run on a time-boxed tick (5 min for Periodic, 6h for Daily, 7d for Strategic). When a skill discovers work that **cannot be completed within its remaining time budget**, it should fork the work into a new `#demiurge.xxx` session rather than:

- Truncating the work and producing a partial result
- Blocking the YOLO tick loop while trying to do too much
- Silently skipping the work because it's "too big"

A forked `#demiurge.xxx` task is equivalent to a human sending a new chat request — it creates an independent session that runs in its own container, with its own token budget, and can take as long as needed. The difference is the **YOLO origin marker**: the forked task carries metadata identifying it as YOLO-originated, so that:

1. Commit messages generated by the forked task follow the active commit convention (see `@system/commit-convention`; default gitmoji) and carry the YOLO origin in the body
1. The forked task's report is routed back to the YOLO cycle report (HubRis `yolo_cycle_report`)
1. The human can distinguish YOLO-forked tasks from human-initiated tasks in the dashboard

## When to Fork

Fork when ALL of the following are true:

1. **The work is non-trivial**: it would require multiple files, multiple steps, or a sequence of skill invocations (e.g., "add regression tests for 61 fixes" is non-trivial; "fix one clippy warning" is trivial).
1. **The work cannot fit in the remaining tick budget**: if the YOLO tick has already consumed significant time on scanning/analysis, and the remediation would require a long skill chain, fork it.
1. **The work has a clear, well-defined scope**: the skill can describe exactly what needs to be done (e.g., "add tests for the modbus validation commits", "split yolo_daemon.rs into submodules"). If the scope is vague, do NOT fork — report the finding and let a human or a higher-tier task define the scope.

## When NOT to Fork

Do NOT fork when:

1. **The work is trivial**: a single mechanical fix (one clippy warning, one import addition). Do it inline.
1. **The skill is read-only by design**: monitoring skills (like `regression_monitor`, `code_health_check`, `agent_liveness_check`) should report findings, not fork remediation tasks — UNLESS the skill's SoP explicitly includes a fork step.
1. **The work requires human judgment**: if the remediation involves architecture decisions, API design choices, or security trade-offs, report it via `report_human` instead of forking. The human decides.
1. **The fork would create a cascade**: if forking would trigger more forks (e.g., a forked task that itself discovers more work), do not fork — escalate to `report_human` for prioritization.

## What a Forked Task Contains

When forking, the skill should compose a task description that includes:

1. **Origin marker**: `[yolo:<skill_name>]` prefix in the task title
1. **Trigger context**: what signal triggered the fork (e.g., "`regression_monitor` detected fix:test ratio of 15:1")
1. **Scope**: the specific work to be done, bounded and measurable (e.g., "add regression tests for the 5 modbus validation commits: 4f943a783, d49f9052c, 0209f80b8, bcbebc9d8")
1. **Suggested skill chain**: which skill(s) should handle the work (e.g., `testing_pipeline`, `auto_fix`, `refactoring_workflow`)
1. **Severity**: the severity level from the triggering skill's analysis
1. **Commit convention**: forked tasks use the active commit-convention preset with the origin noted in the body (default gitmoji e.g., `✅ Add modbus validation regression tests.`) (body: `YOLO origin: regression_monitor`)

## Fork Dispatch Mechanism

The actual mechanism for creating a `#demiurge.xxx` task from within a skill is an engine-level capability. Skills should express the fork intent through their report output, using a structured format that the engine can parse:

```text
FORK_REQUEST:
  title: "[yolo:regression_monitor] Add regression tests for modbus validation fixes"
  trigger: "fix:test ratio 15:1, 8/10 batches with 0 tests"
  scope: "Add tests for commits 4f943a783, d49f9052c, 0209f80b8, bcbebc9d8"
  suggested_skills: ["testing_pipeline"]
  severity: "severe"
```

If the engine does not yet support structured fork dispatch, fall back to `report_human` with the same content — the human can then manually initiate the task. The skill should not attempt to implement the fork mechanism itself; it should express intent and let the engine handle dispatch.
